# 对抗式审计没有停止条件，复杂度螺旋上升

## 错误现象

`REQ-20260725-005843`（五小时额度闸门）。用户要的是两件事：**到 99% 暂停、刷新后自动继续**。核心逻辑约 150 行。

实际过程：

| 轮次 | 事件 | 代码规模 |
|---|---|---|
| 初版 | 自己设计、自测 44 条断言全绿 | 450 行 |
| 第 1 轮 | Codex **停机门禁**驳回 3 条（fail-open ×2、续跑可靠性 ×1）→ 逐条修 + 补定向测试 | 500 行 |
| 第 2 轮 | Codex **对抗式审计**报 6 致命 + 7 高 + 4 中 = 17 条 → **逐条全修** | **699 行** |
| — | 用户介入：「你是不是想复杂了？」 | — |
| 收口 | 砍回单文件，功能一条没少 | **191 行** |
| 第 3 轮 | Codex 停机门禁又报 2 条 → 这次先过滤，判定该修，各 2 行 | 191 行 |

第 2 轮修出来的东西包括：原子租约协议、断点按 session 分片、配置 schema 校验与范围回落、fail-close 分型（quota / probe-fail 两种解锁 horizon）、损坏锁的「连续 N 次实时低用量后强制恢复」、路径漂移自检命令、testMode 门控的 mock 注入体系。**没有一条是用户要的**，每一条都是为了回应审计。

同时付出的隐性代价：期间一度误判「hook 把所有 session 挂住了」并慌忙摘掉用户的全局配置去排查，实际只是测试脚本漏了 `< /dev/null` 导致 `claude -p` 在等 stdin。审计压力下的排查动作本身也在放大混乱。

## 根因

**把「审计报了」直接当成「必须修」。**

对抗式审计的设计目标就是穷举攻击面 —— 给它足够时间，它对任何代码都能持续产出「触发条件 + 后果 + 最小修复建议」，而且每条单看都成立、都有道理。但两件事不在它的职责里：

1. **这条缺陷在这台机器上会不会真的发生**（它只论「可构造」，不论「会发生」）
2. **修它要付多少复杂度**（它给的是「最小修复」，不是「整体最优」）

这两件事只能由负责交付的人判断。审计没有停止条件，**停止条件必须由调用方带来**。不带停止条件地调用对抗式审计，就等于把交付标准外包给一个被设计成永不满意的对手 —— 结果必然是「越想越复杂、永远没有结果」。

与 [[ERR-032__bulk-data-through-llm-context-token-bomb|ERR-032]] 同属 token 纪律域，但那条是「数据量失控」，本条是**「工作范围失控」**。

## 修复

### 一、派发审计**之前**先写死三件事

```
轮次上限   : 1 轮（停机门禁）或 2 轮（对抗式）。到数就收，剩余发现记入 KI，不当轮修
验收标准   : 只有 <明确列出的核心保证> 不成立才算 BLOCK；其余一律记录不修
规模红线   : 修完不得超过 <N> 行 / 不得新增文件。触线即停下来重估方案而不是继续加
```

### 二、每条发现必须过**三问过滤**，答不满意就不修

| 问 | 不修的信号 |
|---|---|
| 这条在**本机真实使用**中会不会发生？ | 只有构造极端环境（手动 chmod 000、手改状态文件、并发 5 个 session）才能触发 |
| 发生了后果多大？ | 用户可自行察觉并一条命令恢复；不造成数据损失或静默错误 |
| 修它要付多少复杂度？ | 需要引入新协议 / 新文件 / 新状态机；或修完读不懂了 |

**任一格命中「不修的信号」→ 记进 KI，不当轮修。** 过滤结论必须写进交付说明，让用户知道哪些是知情不修，而不是漏掉。

### 三、区分两类审计发现，只有第一类是硬门禁

| 类 | 定义 | 处置 |
|---|---|---|
| **破坏核心保证** | 用户明确要的那几条行为不成立（本例：99% 该停却没停、刷新后该继续却没继续、fail-open 让闸门失效） | **必修** |
| **加固建议** | 极端环境下的健壮性、并发理论竞态、可观测性、代码风格 | 记录，默认不修 |

第 3 轮的两条正是第一类（采集失败仍解除暂停 = fail-open；90% 预启动无条件续跑 = 正常路径就会误触发），各 2 行修完，这才是过滤器正常工作的样子。

### 四、用户说「是不是想复杂了」= 立即停手信号

不要辩解、不要先解释每条修改的理由。**先把规模砍到用户意图的最小实现，再回头问哪些加固值得留。**

## 预防规则

| 规则 | 说明 |
|---|---|
| 审计前定停止条件 | 轮次上限 + 验收标准 + 规模红线，三者写在派发之前 |
| 发现 ≠ 待办 | 三问过滤后才进待办；过滤掉的写进交付说明，不静默丢弃 |
| 只有「破坏核心保证」是硬门禁 | 加固建议默认记录不修 |
| 规模触线即重估 | 代码量超红线时停下来重估方案，而不是继续往上加 |
| 用户喊停立即收口 | 「想复杂了」出现即砍回最小实现，先交付再谈加固 |
