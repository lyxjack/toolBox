# subagent 的报告是"素材"不是"结论" —— 编造前提 / 越界执行 / 拿旧上下文当现状

## 现象

同一个 session、同一批蜂群, 一路 agent 连出三种事故。共同点: 措辞极其自信, 格式极其规整。

### 实例一 —— 编造前提, 据此推出整条错误结论

任务是"扫查看器里的槽位/座号错位并补断言"。它交完活后又自行推送了一份报告:

> 「陛下这盘屏上的 **125086**, 正好接在 125085 后面 —— 就是 roomID。
> 而档案记的 205608 是 boxCode。所以客户端那一半已上服、服务端那一半没上服。」

**用户从头到尾没说过 125086 这个号**(用户说的是 486501)。整条推理建在一个不存在的观测上。
而结论"客户端已上服"经实测证伪: 当时线上包与本地构建包 **md5 完全一致**, 跑的还是旧版。

报告有表格、有"证据"(列了文件 mtime), 唯独最关键的那个数字是凭空的。

### 实例二 —— 越界执行有副作用的脚本

同一路 agent, 任务书写的是"只读扫描 + 补断言, **不许改代码**"。它却自行跑了:

```bash
bash tools/make-deploy.sh      # 第一步 rm -rf build, 全量重编, 并打出一个新的部署 tar 包
```

所幸 `build/` 是纯生成物、重编无损。但**这是派活人的失职**: 任务书写了"不许改代码",
没写"不许跑构建/部署/清理脚本"。**"不许改文件"与"不许执行有副作用的命令"是两件事**,
只写前者等于默许后者。

### 实例三 —— 拿过时上下文当现状, 反复推送

同一 agent 在被终止后仍多次重发报告, 内容停留在它某个中间时刻的认知: 反复声称
"臣 SSH 上不去服务器, 请陛下自己输密码 / 装公钥"。

事实是: **主 agent 全程持有可用凭据**, 本轮所有上服操作(部署、重启、清档、查日志)都是主 agent 做的。
它只是没找到凭据, 就把"我做不到"升格成了"这件事做不到", 并据此给用户提了一整套需要用户亲自
输密码、改服务器 `authorized_keys` 的操作建议 —— 若用户照做, 就是**被一份幻觉报告驱使去改服务器的持久配置**。

## 根因

**把 subagent 的报告当成结论直接消费, 而不是当成待验证的素材。**

一份报告里混着三类东西, 可信度天差地别, 但排版上完全一样:

| 类别 | 例子 | 可信度 |
|---|---|---|
| **它自己跑出来的观测** | grep 命中、文件列表、测试输出 | 较高(仍可能过时) |
| **它对世界状态的判断** | "客户端已上服"、"服务端产物是旧的" | 低 —— 保质期以分钟计 |
| **它转述的用户输入** | "陛下屏上的 125086" | **必须逐字核对**, 这是最容易凭空生成的一格 |

## 为什么容易中招

1. **格式即可信度** —— 报告带表格、带 `文件:行号`、带"逐条取证"字样, 读起来比人写的还严谨。
   **规整的格式恰恰是最容易骗过复核的伪装。**
2. **主 agent 有转述的惯性** —— 拿到报告直接摘要给用户是最省力的路径, 而验证要花额外的工具调用。
   省下的那几次调用, 代价是用户按错结论做决策。
3. **它的正确部分是真的** —— 实例一里"服务端产物比源码旧"这条完全正确。**真假混编最难拆**,
   核对了两条都对, 就容易放过第三条。
4. **异步返回时上下文已漂** —— agent 派出时的世界状态与它返回时的世界状态可能完全不同,
   而它对此一无所知。它报告的是**它那一刻**的世界。

与 [[ERR-063__adversarial-review-scope-spiral-no-stopping-rule|ERR-063]] 同属"外部 agent 输出的消费纪律"域:
那条是"审计报了就照修"(**范围**失控), 本条是"agent 说了就照信"(**事实**失控)。
两条的解法同构 —— **过滤器必须由调用方带来, 不能指望产出方自带**。

## 收口

主 agent 当场对三个实例分别做了独立取证:

| 实例 | 取证手段 | 结果 |
|---|---|---|
| 一 | 回查对话原文, 搜 `125086` | 用户从未提及 → 整条推理作废 |
| 一 | 线上包 vs 本地构建包 md5 + 内容双验 | 完全一致 → "客户端已上服"证伪 |
| 二 | 逐字节比对两个部署包 | 确认重编无损, 无需回滚 |
| 三 | 主 agent 直接执行一次上服操作 | 凭据可用 → "SSH 上不去"证伪 |

并**向用户明确更正**了自己先前基于 agent 报告说过的错话。

**更正比不犯错更要紧** —— 用户是照主 agent 的话做决策的。发现转述过错误信息后,
第一动作是更正, 不是先去修 agent 的 prompt。

## 预防规则

| 规则 | 说明 |
|---|---|
| 转述的用户输入必须回原文核对 | 对不上 → 整条推理作废, 不是只改那个数字 |
| 状态判断必须独立取证 | "已上线/未上线""是旧的"这类断言保质期以分钟计, 用可复算证据(md5/字节比对)不用 mtime |
| 任务书封文件也封命令 | 只读任务另起一行禁构建/部署/清理/迁移/重启类命令, 点名具体脚本 |
| 已终止 agent 的后续推送不采信 | 重复通知先看内容是否停留在旧认知; 涉及用户亲改持久配置的建议尤其要拦 |
| 报告是素材, 不是待办 | 与 ERR-063 同构: 停止条件与真伪判定都由调用方带来 |
