# 七组数据全是 5.00 秒，而玩家一秒也没看见 —— 精确地量错了命题

## 案发

需求原句：**「对局结束…会显示剩余手牌给所有人，然后五秒过后才会弹出结算」**。

上服后作者交出的验收证据：

```
房125154  09:34:50.571 → 09:34:55.567   5.00s
房125153  09:40:31.587 → 09:40:36.587   5.00s
房125157  09:42:41.887 → 09:42:46.891   5.00s
…七次配对，4.99 / 5.00 / 5.02
两条实现路径都在现网跑过（小局 8 次 + 终局 2 次）
Settle 报文实抓到 remainCards
```

结论写的是「功能已生效」。用户随后打了两把，反馈：**「都没有五秒间隔」**。

## 根因

作者度量的是 **`G_GD_Settle` 与下一条广播之间的墙钟间隔**；需求要的是 **玩家眼睛里残牌停留的时长**。

两者在多小局模式下恰好等价（小局不弹结算面板），于是看着对；在单局的经典模式下**不等价** —— 结算面板与残牌同帧上屏，面板是 1280×720 遮罩 + 四张 240×350 的卡，四个出牌槽逐一落在卡盒内（`rootSettle` 绘制序 32 > `nodeOut` 24），残牌 0 帧可见。那 5 秒一秒不少地过了，**全花在面板底下**。

## 为什么这次特别难自查

**度量越精确，错误结论越有说服力。** 七组数据、两条路径、报文实抓 —— 证据链看上去无懈可击，作者自己先被说服了。真正的问题是这条证据链**从头到尾没有一个环节触及「可见」**。

其余三个放大器：

| # | 放大器 |
|---|---|
| 1 | **两个功能各自验过，从未合验。** 结算面板单独验（四种胜负组合逐一过目），残牌单独验（多小局模式）。经典模式恰是两者**必然相遇的唯一模式**，而它落在两份验收清单之间的缝里 |
| 2 | **自己写的注释成了自己的证据。** 代码注释里写着「四张卡与出牌槽不重叠，互不遮挡」—— 这句从未实测过，却在后续几轮排查里被反复当作事实引用（同 [[ERR-111__node-box-used-as-visual-evidence\|ERR-111]]） |
| 3 | **落盘断言全是源码级**，钉得住「服务端 await 了 5 秒」，钉不住「牌在屏上可见 5 秒」。断言全绿是真的，覆盖不到才是事实 |

## 预防规则

1. **验收判据必须写成玩家可观察的句子。** 「玩家能看到 X 持续 N 秒」是判据；「服务端 await N 秒」是机制。定判据前把需求原句抄下来，逐词对照自己打算量的那个量 —— 对不上就是量错了命题。
2. **报告用词区分「机制已生效」与「需求已满足」。** 只测了前者就只报前者，不得升格。本案若如实写成「服务端按住已实测 5.00s，玩家侧可见性未验」，用户当场就会问那一句。
3. **新元素与既有全屏/高层 UI 共存时，必须显式验 z 序与包围盒。**「不重叠」这类话未经实测不得写进注释 —— 写进去就会被当成事实引用。
4. **每个功能自问一句：「如果它完全没生效，哪条断言会红？」** 答不上来，说明守着的只有机制。本案答案是「没有一条」。
5. **两个功能相遇的模式，必须单列一条验收。** 逐个验过不等于合流处验过；缝隙恰恰在两份清单之间。

## 与近邻的区别

- [[ERR-096__assertion-pinned-to-the-wrong-quantity|ERR-096]] 是**断言**钉错了量（代码里的守卫）；本条是**验收证据**证错了命题（交付时给人看的东西）。
- [[ERR-111__node-box-used-as-visual-evidence|ERR-111]] 是**证据面**不对（拿节点框冒充像素）；本条的证据面（服务端日志墙钟）完全可信，**错在它证明的不是那个命题**。
- [[ERR-105__fixture-collapses-phases-so-the-gap-cannot-exist|ERR-105]] 是夹具让现象不可能出现；本条是现象真的出现了，只是没人去看那一面。

> CI: Tier 2 only —— 「判据是否落在玩家可观察面」是语义判断，静态规则表达不了。落地方式：交付前自检「我量的这个量，和需求原句里的那个量，是同一个吗？」
