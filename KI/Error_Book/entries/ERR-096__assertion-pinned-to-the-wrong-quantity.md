# 断言钉错了量 —— 守住的不是不变量, 是一个碰巧相关的数字

## 场景

同一天在三处独立改动里抓到同一个形态: 断言写了、跑了、全绿, 但它守的根本**不是本轮要修的那个缺陷**。

主案是掼蛋结算四卡的身份错位: 修法是加一张显式换算表 `SETTLE_SLOT_BY_VIEW = [0,3,1,2]`,
配套写了 46 条落盘断言, 其中 ④ 段用正则从 `.ts` 里抠出这个常量、断言它恰等于 `[0,3,1,2]`。
**46 条全绿。**

另两处是记牌器与结算面板的遮挡让位、复盘查看器的视角锚点;
再加上结算卡昵称 Label 的几何前提, 共四例。四例的共同结构:

> **断言钉的那个量, 既不代表意图, 也不由自己掌控。**

## 根因: 断言钉在了「看起来相关」而非「真正要守」的量上

### 变体一 —— 只验「常量存在」, 没验「常量被用上」(假绿)

Codex 对抗审计做了一次变异: **常量 `[0,3,1,2]` 原样留着不动**, 只把实际取卡那一行改回

```ts
const c = this.settleCards_[v]   // 裸 view 下标, 换算表形同虚设
```

**46 条照样全绿。**

也就是说: 这份断言守不住它本该守的那个缺陷。「常量在」证明不了「常量接入了生产路径」,
而本轮真正修掉的恰恰是取卡那一行 —— 常量只是修复的**材料**, 不是修复本身。

同一形态在另外两处复现:

| 处 | 断言钉的量 | 保留该量、仍能复现缺陷的变异 |
|---|---|---|
| 记牌器/结算面板遮挡 | `yieldCounterForSettle` 方法存在 | 方法在, 但 `buildSettlePanel` / `closeSettlePanel` 两条路都不调它 |
| 复盘查看器视角锚点 | `seatSlot()` 换算写得正确 | `seatSlot` 再对, `renderSeat` 取 DOM 走的是裸座号 → 整套机制是死代码 |

两处的共性: 只测那个"零件"的断言, 在缺陷完整存在时也全绿。

### 变体二 —— 钉了「引擎自己拥有、会重算」的属性(必然腐烂)

结算卡昵称 Label `lblName` 的 `overflow` 是 `NONE` ——
**Cocos 在这个模式下会按文字内容自动改节点 contentSize**。
而断言的 ⓪ 段把「`lblName` 盒 190×40」当作几何前提钉了进去。
那个 190×40 是手工设的, 引擎一碰就按「本家」两个字重算成 51.99×50.4。

结果: 断言在某个时刻由绿转红 **8 条**。排查时第一反应是"谁把 prefab 改坏了",
差点冤枉正在编辑器里改东西的用户。查文件 mtime 才发现 prefab 从更早就是这个状态 ——
**不是谁改坏了, 是断言把一个自己不掌控的量当成了基准。**

## 为什么自查没抓到

四个理由叠在一起, 让这类假绿比"根本没有断言"更难发现:

1. **它绿**。红的断言会被追查到底, 绿的断言没人会去质疑。
2. **它看起来很对**。常量值断言、几何尺寸断言, 都是断言里最"标准"的形态 —— 形态越标准越没人重读。
3. **它把注意力从真正的不变量上引开**。写完那 46 条, 人会真心以为"这个缺陷再也回不来了", 于是不再手工验。
4. **变体二还会反过来诬告别人**。断言由绿转红时, 第一嫌疑人永远是最近动过文件的那个人 —— 真凶却是断言自己选错了基准。

变体一这个洞同样是**对抗审计变异出来的**, 不是跑测试跑出来的;
审计的停机规则见 [[ERR-063__adversarial-review-scope-spiral-no-stopping-rule|ERR-063]]。

## 修复

三处一律补「接入生产路径」断言 —— 抠出**调用方的函数体**, 在体内做正向 + 负向双断言:

| 处 | 新增段 | 正向 | 负向 |
|---|---|---|---|
| 结算四卡 | ⑤ | `applySettleContract` 体内引用换算表, 取卡下标是换算出来的变量 | 体内不得出现裸 view 取卡 |
| 记牌器让位 | ⑩ | `buildSettlePanel` 以 `true`、`closeSettlePanel` 以 `false` 调 `yieldCounterForSettle` | 让位方法内不得写 localStorage(那会把玩家的开关偏好永久改掉) |
| 复盘锚点 | ⑨ | `renderSeat` 取 DOM 走 `seatSlot()` 的结果 | 不得出现裸座号取 DOM |

变体二则改成**受控形态**: Label 的 `overflow` 由 `NONE` 改成 `CLAMP`, 尺寸重新归自己掌控,
190×40 才有资格当基准。

**负控实证**(每条新断言都按 [[PAT-035__negative-control-before-trusting-a-new-assertion|PAT-035]]
先反证再采信): 三处变异分别报红 **3 / 1 / 44** 条 —— 尤其是结算那一处, 加 ⑤ 段之前
同一变异 0 报红, 加完 3 报红, 差值本身就是"这份断言到底新守住了什么"的证明。

收口计数:

- `gunZi_Resource/kds-game-gd/test/settleCards.assert.mjs` 46 → **52** 条(新增 ⑤"接入生产路径")
- `test/cardCounter.assert.mjs` 178 → **217** 条(新增 ⑨ 显隐/启用、⑩ 遮挡让位的代码路径断言)
- `test/replayViewer.assert.mjs` **274** 条

## 泛化

**断言必须钉在「你真正想守的那个不变量」上。钉一个看起来相关、但既不代表意图、
也不由你掌控的数字, 等于没钉 —— 而且它会绿, 绿得你以为守住了。**

危险信号:

- 断言的宾语是**定义点**(常量的值、方法的存在、文件里有某个符号), 而缺陷发生在**调用点**
- 断言读的是框架/引擎能重算的属性: 自动布局尺寸、自动生成 id、时间戳、序列化顺序
- 断言与被测实现引用同一份来源(自证), 变异其一另一个跟着变
- 修完缺陷补的断言, 说不出"它在修复前会红几条"

正确姿势: 每写完一条就问「能不能构造一个变异体, 它保留我断言的这个量、却仍然复现原缺陷」——
能, 这条就是假的。这一问必须**在写断言的当下**做, 而不是等对抗审计替你做。
