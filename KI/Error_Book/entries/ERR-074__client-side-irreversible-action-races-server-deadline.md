# 客户端替玩家自动过牌, 三轮都没赶在服务端超时之前

## 需求背景

掼蛋出牌时限统一 20 秒。当玩家手里没有任何一手压得过桌面牌(只能过)时,
本地倒计时缩到 5 秒并**自动替他过牌** —— 省掉干等。

服务端恒下发 20 秒(单一真值), 缩短只做在客户端本地。

## 错误现象

三轮翻车, 每轮都以为修好了:

| 轮次 | 实现 | 漏在哪 |
|---|---|---|
| ① | 只能过 → 固定 `startTimer(5)` | 完全没看服务端剩余时间 |
| ② | `Math.max(1, Math.min(5, serverSec - 1))` | 服务端秒数向下取整, 报 1 秒实际可能剩 0.1 秒; 地板逼客户端等满 1 秒, 仍晚 |
| ③ | 地板改 0, 令 `0 = 立刻过` | `0` 在服务端侧语义重载: 既是「不限时房」又是「剩余不足 1 秒」, 客户端把后者误当前者, 给了满 5 秒 |

**后果统一**: 服务端先一步超时 → `setUserTuoguan(seat, true)` → 玩家被转**托管**,
此后每回合只有 2 秒且由 `GDAuto` 代打, 必须手动点托管按钮才解得开。
比"白等几秒"严重得多 —— 玩家会觉得"我明明在操作, 怎么被系统接管了"。

## 根因

三层叠加:

1. **时间字段的消费方没有假设最坏值**。`gdRoomData.remainTurnSec` 用 `Math.floor(remain/1000)`,
   报 N 秒的真实剩余是 `[N, N+1)` 秒。报 1 秒 ≠ 还有 1 秒可用。
2. **`0` 这个值语义重载**。`remainTurnSec` 有四条路径吐 0: 不限时房、已超时、
   剩余不足 1 秒(`Math.floor(0.9)=0`)、无回合缓存。客户端只能看到一个 0, 无从区分。
3. **测试钉的是样例点不是不变式**。旧断言 `if (sec > 1) expect(got).toBeLessThan(sec)`
   恰好把 `sec=1` 排除在外, 而那正是出事的格子。

## 修复

**两侧各守一半契约:**

- **服务端收口语义**: `remainTurnSec` 对限时局最低报 1 秒、绝不吐 0 ——
  `0` 从此只属于「不限时」这一个含义。
- **客户端按最坏值算**: `onlyPassCountdownSec(serverSec, onlyPassSec)` 返回
  `max(0, min(onlyPassSec, serverSec - 1))`, 且**返回 0 表示「立刻执行, 别起倒计时」**
  (不是「不计时」)。调用方收到 0 当场过牌。
- **调用次序**: 当场过牌的分支移到 `updateActionBarForTurn()` 之后, 免得防重锁被清掉。

**测试双侧钉桩**(缺一不可):

- 客户端侧: 定义域 1..60 秒逐格断言 `本地秒数 < 服务端剩余秒数`(严格小于)
- 服务端侧: 0~30 秒逐 100ms 扫描, 断言限时局 `remainTurnSec` 恒不为 0

单守一边都不够 —— 客户端的 `0 → 满额` 分支完全依赖服务端不吐 0 这条约定。

## 泛化

凡是「客户端在本地计时后替用户执行不可逆动作」的设计(自动过牌 / 自动放弃 /
自动提交 / 倒计时结束自动跳过), 都要过这三关:

1. 本地时限是否**严格早于**服务端权威时限? 写成不等式, 对定义域全扫。
2. 服务端下发的时间字段是否**向下取整**? 是则按 `[N, N+1)` 的下界算。
3. 时限算下来 ≤0 时是**当场执行**还是**退化成等 1 个单位**? 后者是伪修复。

参见 [[PAT-034__server-authoritative-clock-with-local-fast-path|PAT-034]] 的分层做法,
以及 [[ERR-075__incremental-path-fixed-snapshot-path-forgotten|ERR-075]] —— 同一次改动里
另一条"增量修了、快照忘了"的漏网路径。

## 补遗① (2026-07-28 当日): 语义收缩后, 哨兵值从「合法」变成「只可能是故障」

本条正文里为收口 `0` 的语义, 做法是"服务端限时局最低报 1 秒, `0` 只留给不限时"。
**几小时后产品决定取消「不限时」档**(三档改为 30/20/15 全限时)。于是:

```
取消前: remainTurnSec 返回 0  ⇒  合法语义(不限时房)
取消后: remainTurnSec 返回 0  ⇒  **只可能是故障**(setTurn 漏调 / 计时缓存失真)
```

原来的兜底代码一字未动, 但它的**性质变了** —— 从"正确处理一种合法情形"变成
"把故障静默伪装成合法情形":

- 服务端吐 0 → 客户端 `onlyPassCountdownSec(0, 5)` 把它解释为"无 deadline", 返回满额
- 客户端于是不掐表、慢悠悠等 5 秒, 而服务端的 deadline 其实**还在跑**
- 结果又绕回本条正文那个坑: 玩家被转托管

### 预防规则

**枚举/档位收缩(删掉某个合法取值)时, 要回头审所有为它写的兜底分支**:
那些分支不会因为取值消失而自动消失, 它们会**默默改行**去掩盖故障。

判据: `grep` 该 sentinel 值(`0` / `-1` / `""` / `null`)的全部消费点, 逐个问
"这个值现在还可能合法出现吗?" —— 答案若是"不可能", 那么这条分支就该:

- 记一行**错误日志**(让故障有迹可循), 且
- 采取**明确的 fail-safe**(本案: 客户端不启用快过, 退回普通倒计时让玩家自己决定,
  绝不替他做不可逆动作), 而不是继续走那条已经名不副实的"合法"路径

同类"合法值退役"信号: 功能开关下线、状态机删相位、协议字段废弃。
资产/文案侧的同类清扫见 [[ERR-078__edited-one-asset-variant-assertion-covered-only-that-one|ERR-078]]
(一张档位表散落八处承载点)。
