# Audit Ledger Mode
# Version: 1.0

---

## 1. 触发条件

涉及以下任务类型时强制创建独立 audit 工件:

| 任务类型 | 示例 |
|---------|------|
| 代码审计 | 代码质量评审、安全审查 |
| 架构审计 | 模块依赖分析、架构合规检查 |
| 重复 Skill 审计 | duplicate_review 更新 |
| 修复验证 | 返工后的回归确认 |
| 高风险变更复核 | 数据库迁移、核心模块重构 |
| QA 整改跟踪 | 多次返工的根因分析 |

## 2. Audit 工件规范

### 2.1 创建位置
```
.in-process/audit/{date}__{project}__audit__{id}__{slug}.md
示例: 20260307__myapp__audit__001__skill-dedup-review.md
```
使用模板: `Agent/templates/audit_ledger.tmpl.md`

### 2.2 必须记录的内容

| 章节 | 职责 | 何时写 |
|------|------|--------|
| **Audit Scope** | 本次审计覆盖什么 | 创建时 |
| **Findings Summary** | 发现总览(数量、严重度分布) | 审计完成时 |
| **Detailed Findings** | 逐条发现:ID、严重度、描述、证据、影响 | 审计过程中追加 |
| **Remediation Tracking** | 每条 finding 的整改状态 | 整改过程中更新 |
| **Verification Result** | 整改后的复测结果 | 复测后填写 |
| **Audit Conclusion** | 最终结论和建议 | 全部完成后 |

### 2.3 Finding 严重度

| 级别 | 含义 | 整改要求 |
|------|------|---------|
| **CRITICAL** | 阻塞交付或存在安全风险 | 必须整改,不可延期 |
| **HIGH** | 功能缺陷或重大质量问题 | 本次 run 内整改 |
| **MEDIUM** | 质量问题但不阻塞功能 | 建议本次整改,可延期 |
| **LOW** | 改进建议 | 记录即可,择机处理 |
| **INFO** | 信息性发现 | 无需整改 |

### 2.4 Remediation 状态

```
OPEN → IN_PROGRESS → FIXED → VERIFIED → CLOSED
                  ↘ WONT_FIX → CLOSED (需记录原因)
                  ↘ DEFERRED → (移入 project memory)
```

## 3. Plan 与 Audit 的分工

```
┌─────────────────────────────────┐     ┌─────────────────────────────────┐
│            PLAN                 │     │            AUDIT                │
├─────────────────────────────────┤     ├─────────────────────────────────┤
│ ✅ 行动步骤                      │     │ ✅ 问题发现                      │
│ ✅ 文件追踪 (read/modify)        │     │ ✅ 证据记录                      │
│ ✅ 范围和约束                    │     │ ✅ 整改追踪                      │
│ ✅ 阶段进度                      │     │ ✅ 复测结果                      │
│ ✅ 风险和阻塞                    │     │ ✅ 审计结论                      │
│ ✅ 下一步动作                    │     │ ✅ 严重度分级                    │
├─────────────────────────────────┤     ├─────────────────────────────────┤
│ ❌ 不记录 finding 详情           │     │ ❌ 不记录执行步骤               │
│ ❌ 不做严重度分级                │     │ ❌ 不追踪文件读写               │
│ ❌ 不追踪整改状态                │     │ ❌ 不做阶段规划                 │
└─────────────────────────────────┘     └─────────────────────────────────┘
```

**联动规则**:
- Plan 中发现的问题 → 创建 Audit finding,plan 中引用 audit ID
- Audit 中的整改动作 → 在 plan 的 Steps 中增加整改 step
- 两者必须交叉引用,但不合并为一个文件

## 4. Audit 生命周期

| 状态 | 含义 |
|------|------|
| `active` | 审计进行中 |
| `pending_remediation` | 审计完成,等待整改 |
| `closed` | 所有 finding 已 CLOSED/VERIFIED |
| `archived` | 移入 .in-process/archive |

**保留规则**: Audit 是正式合规记录,**永不删除**,只归档。
